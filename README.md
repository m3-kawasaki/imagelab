# ImageLab

**画像処理の「中身」を、その場でつまみを動かして見るためのブラウザ道具です。**

→ **[ここで動きます](https://m3-kawasaki.github.io/imagelab/)**（インストール不要。読み込んだ画像は端末の外に出ません）

レタッチソフトのボタンの内側で何が起きているのかを、
勉強会で画面共有しながら見せるために作りました。仕上げの道具ではありません。

---

## 何ができるのか ── 写真のお悩み6景

いちばん手早い入口は、次の6つです。左の処理リストから選んで、右のつまみを動かし、
キー `3`（原画）と `2`（処理後）を交互に押すと、変化がはっきり分かります。

| お悩み | 使う処理 | 見えること |
|---|---|---|
| **逆光で手前が真っ黒** | トーンカーブ／CLAHE | 空を白飛びさせずに影の中だけを起こせる。全体を明るくするのとは違う |
| **暗い場所でザラつく** | ノイズ除去の比較 | ぼかせば粒は消えるが顔もぼける。バイラテラルなら輪郭を残して粒だけ取れる |
| **なんとなく眠い・甘い** | アンシャープマスク | 「シャープ」の正体は、ぼかした絵との差を元に足し戻しているだけ |
| **雑誌をスキャンしたら網目が出た** | ノイズ付加（周期）→ スペクトルマスク | 写真を「模様の楽譜」に開いて、縞の音符だけ消して戻す。**山場はここ** |
| **広角で建物が歪む・傾く** | レンズ歪みと補正／アフィン変換 | 曲がった柱がまっすぐ戻る。傾き直しは画素の作り直しでもある |
| **影の落ちた書類が読めない** | 二値化（大津／適応的） | 写真全体で1つの境目を決めると潰れる。画素ごとに決めれば読める |

そのほか、エッジ検出（Sobel・Canny の6段階）、周波数フィルタ、モルフォロジー、
デモザイク（Bayer 配列 → バイリニア vs AHD）まで **22の処理**が入っています。
一覧は下の「実装している処理」、解説は [`docs/処理解説.md`](docs/処理解説.md)。

### 作りについて

- **ビルド不要。** 素の HTML / CSS / JavaScript だけで、外部ライブラリを1つも使っていません。
  FFT も自前です（[`js/fft.js`](js/fft.js)）。中身を見せることが目的の道具なので、そうしています
- **画像は端末の外に出ません。** すべてブラウザの中で計算します。送信も保存もしません
- **重い処理は Web Worker が複数コアで分担**します。計算中も画面は固まりません
- **`index.html` をダブルクリックしても動きます**（`file://` で直接。サーバ不要）。
  ページを保存して手元で開けば、ネットにつながっていなくても使えます

## 使い方

上の[公開ページ](https://m3-kawasaki.github.io/imagelab/)を開くか、
一式をダウンロードして `index.html` を **ダブルクリックするだけ**。サーバは不要です。

読み込んだ画像はブラウザの中だけで処理され、外部には一切送信されません。

### 画面

| 場所 | 中身 |
|---|---|
| 左 | 処理リスト（カテゴリ別） |
| 中央 | ビューア。分割スライダー／ルーペ／差分表示 |
| 右 | パラメータ と 解説 |
| 下 | ヒストグラム／ラインプロファイル／計算時間と実行経路 |

### 覚えておくと便利なもの

- **キー `1` `2` `3` `4`** … 表示を 分割／処理後／原画／差分 に切り替え。画面共有中に手早く切り替えられます
- **分割スライダーの丸いつまみ** … ドラッグすると原画と処理後の境目が動きます
- **ルーペ** … マウス追従。倍率はスライダーで変更。中央の赤枠が1画素です
- **逐次表示** … 重い処理の途中経過を、処理済みの帯が上から降りてくる形で見せます。
  実演向けなので既定はオン。作業中に鬱陶しければ切ってください（**設定は次に開いたときも残ります**）。
  なお**既定の 640 では速すぎて見えません**（バイラテラルが8並列で 0.1 秒で終わるため）。
  見せたいときは下の「実演で分担のようすを見せる設定」を使ってください
- **URL の後ろにハッシュ** … 見せたい状態を直接開けます
  - 例：`index.html#op=canny&sample=geometry&mode=result`
  - `op` は処理 ID、`sample` はサンプル ID、`mode` は `split` / `result` / `source` / `diff`
- **作業解像度** … 既定は長辺 640。スライダーを動かしながら見せられる速さを優先しています。
  細部を見たいときだけ 1024 以上に上げてください（下の「処理時間の目安」参照）

写真の持ち込み方は `samples/README.md` を見てください。

## 実装している処理

| カテゴリ | 処理 |
|---|---|
| 点処理 | トーンカーブ（PCHIP補間）／ガンマ補正／ヒストグラム平坦化／CLAHE |
| 空間フィルタ | 平均化・ガウシアン（分離可能）／メディアン／バイラテラル／アンシャープマスク |
| **周波数領域** | **FFT スペクトル／周波数フィルタ／スペクトルマスク（手で塗る）** |
| **ノイズと評価** | **ノイズ付加（ガウシアン／ソルト＆ペッパー／ショット／周期）／ノイズ除去の比較（PSNR・SSIM つき）** |
| エッジ検出 | Sobel・Prewitt・Scharr／Laplacian・LoG／Canny（段階表示つき） |
| **二値化とモルフォロジー** | **二値化（固定閾値／大津の判別分析法／適応的）／モルフォロジー（膨張・収縮・オープニング・クロージング・トップハット）** |
| **センサと幾何** | **デモザイク（Bayer 配列 → バイリニア vs AHD、PSNR・SSIM・偽色の量つき）／アフィン変換（回転・拡大・せん断）／レンズ歪みと補正（樽型・糸巻き型）** |

各処理の解説は `docs/処理解説.md`（アプリの解説パネルと同じ文章）。

重い処理（バイラテラル／メディアン／ガウシアン σ大／周波数領域の3処理／
ノイズ除去の比較／デモザイク）は Web Worker に逃がします。計算中も画面は固まりません。

**設計書の第1〜第3階層はすべて実装ずみです**（2026-09-06）。
**画面確認（`_checklist.md` の全48項目）も 2026-09-10 に完了しました。**

### 幾何変換の2処理

| 処理 | 何ができるか |
|---|---|
| **アフィン変換** | 回転・拡大縮小・せん断・平行移動。補間3種（最近傍／バイリニア／バイキュービック）と縁の扱い3種を切り替えられる |
| **レンズ歪みと補正** | 樽型・糸巻き型を作る／歪んだ絵を補正する／往復させて誤差を見る。格子を重ねてから歪ませられる |

どちらも**逆写像**で回します。入力の画素を行き先へ飛ばす（順写像）と隙間が空くので、
出力の画素ごとに「もとの画像のどこを読むか」を求めます。読む場所は小数になるので、
そこで補間が要ります。補間の実装は `js/core.js` の `U.sampleImage` に1つだけ置き、
2つの op が共有しています。

**〈往復させて誤差を見る〉が補間の値打ちを数字にします。**変換してから逆変換で戻すと、
理屈のうえでは原画に戻るはずですが戻りません。補間を2回通るからです。
このとき数値は「行きと戻りの両方で画像の中を読めた画素」だけで測っています
（画面の外へ出た隅はそもそも情報が無いので、そこまで数えると
補間の損ではなく隅の黒さを測ることになります）。

### 周波数領域の3処理

2次元 FFT は Cooley-Tukey（radix-2・反復版）を自前で実装しています（`js/fft.js`）。
外部ライブラリは使いません。

| 処理 | 何ができるか |
|---|---|
| **FFT スペクトル** | 対数パワースペクトル／位相／「振幅だけ・位相だけで再構成」の見比べ |
| **周波数フィルタ** | ローパス／ハイパス／バンドパス／バンドストップ／ノッチ。切り方は理想・ガウシアン・バターワースの3種 |
| **スペクトルマスク** | 右パネルのスペクトルを**筆で塗って**遮り、逆 FFT する。ここが目玉 |

**スペクトルマスクの操作**

- 右パネルのスペクトルを**ドラッグ**＝遮る／**右ドラッグ**＝戻す
- 筆は**必ず点対称の位置にも乗ります**。実数画像のスペクトルは点対称なので、
  片側だけ消すと逆変換の結果に虚部が残って絵が壊れるためです
- プリセット（ローパス／ハイパス／バンドパス／十字）から始めて筆で足し引きするのが手早い
- 「ビューアに出すもの」を**マスクを掛けたあとのスペクトル**にすると、
  中央の大画面でスペクトルを確認できます。遮った場所には赤みが乗ります。
  **大きいほうで位置を指しながら、右で塗る**のが画面共有での使い方です
- マスクは正規化周波数を 128×128 に等分した固定の格子で持つので、
  作業解像度を変えても画像を差し替えても塗り直しは要りません
- **どこを塗ればいいかは黄色い破線が教えてくれます。**周りから突出した輝点を
  自動でさがして印をつけ、いちばん強いものには「ここ」と添えます。塗ると印は消えるので、
  狙った場所を押さえられたかがそのまま分かります。人にさがしてもらいたいときは
  「目立つ輝点に印をつける」のチェックを外してください（設定は次に開いたときも残ります）。
  周期的な模様が無い画像では印は出ません（`js/fft.js` の `IL.spectrumPeaks`）

### ノイズと評価の2処理

| 処理 | 何ができるか |
|---|---|
| **ノイズ付加** | ガウシアン（読み出しノイズ）／ソルト＆ペッパー（欠陥画素）／ショット（光子数のゆらぎ）／**周期（斜め縞）**。原画との PSNR・SSIM を表示 |
| **ノイズ除去の比較** | ノイズを乗せてからメディアン・バイラテラル・ガウシアンの3手法で消し、4面を並べて PSNR・SSIM を比べる |

**横並び比較の見せ方**

ビューアは「原画1枚 ⇄ 処理後1枚」の作りなので、3手法を並べる場所がありません。
そこで表示を2通り用意しました。数値は**どちらの表示でも3手法ぶんそろって出ます**。

| 表示 | 見え方 | 使いどころ |
|---|---|---|
| **4分割で並べる**（既定） | 1枚の中に4面を貼り合わせ。見出しと数値はビューアが重ねて描く | 実演。一目で優劣が分かる |
| 1手法（全解像度） | ふつうの1画面。分割スライダーで原画と比べられる | 精査。粒の立ち方を見る |

4分割は各面が縦横とも半分の解像度になります（4面とも同じ縮め方なので比較は公平です）。
粒まで見たいときは1手法に切り替えるか、ルーペを当ててください。

見出しと数値は画素ではなく**ビューアに重ねて**描いています（ルーペには映らないので、
拡大したいときに邪魔になりません）。ただし［保存］だけは別で、
記事に貼れるように**見出しを焼き込んだ PNG** を書き出します。

**見どころは2つ。**
1つめは「万能な手法は無い」こと。ソルト＆ペッパーはメディアンの圧勝ですが、
ガウシアンノイズではメディアンが最下位に落ちます。
2つめは「物差しによって答えが変わる」こと。★は PSNR と SSIM の列ごとに付くので、
**2つの★が別の手法に付くことがあります**（既定の設定がまさにそれです）。

ノイズの乱数は座標から直接作っています（位置ハッシュ）。順番に引く乱数だと
行帯に分けたときに帯ごとの乱数列が食い違い、継ぎ目が横縞になって出ます。

## 作りの方針

- **ビルドなし・外部ライブラリなし。** 素の HTML / CSS / JS だけ
- **ES Modules を使わず classic script。** `file://` で直接開けるようにするため
  （ES Modules は `file://` では Chrome にブロックされます）
- **Canvas 2D の `ImageData` を直接操作。** 中身が読めることを優先し、WebGL は使わない
- 対応ブラウザは Chrome / Edge の最新版。互換シムは書かない

### ファイル構成

```
imagelab/
├── index.html          … 画面の骨格と <script> の並び
├── _selfcheck.html     … 開発用。全処理・全サンプルを総当たりして例外を検出する
├── _checklist.md       … 開発用。自動チェックでは見られない「画面の見え方」の確認手順
├── css/style.css
├── js/
│   ├── core.js         … ImageData ⇄ プレーン変換、畳み込み、ヒストグラム
│   ├── fft.js          … 2次元 FFT（自前実装）とスペクトル表示の道具立て
│   ├── registry.js     … 処理の登録テーブル。UI はこれを読んで自動生成される
│   ├── worker.js       … 重い処理を Web Worker に分担させる実行係
│   ├── samples.js      … 合成テストチャートの生成
│   ├── viewer.js       … 分割スライダー・ルーペ・差分・逐次表示
│   ├── histogram.js    … 下部2つのグラフ
│   ├── main.js         … 画面制御
│   └── ops/            … 1処理＝1ファイル
├── samples/            … 写真の置き場所（README 参照）
└── docs/
    ├── 処理解説.md      … js/ops/*.js から自動生成
    ├── _selftest.js    … 開発用。画像処理の中身を DOM 抜きで検証（node docs/_selftest.js）
    ├── _bench.js       … 開発用。処理時間の計測（node docs/_bench.js 640 480）
    └── _gen_docs.js    … 開発用。処理解説.md を生成
```

### 処理を1つ足す手順

1. `js/ops/` にファイルを1つ置き、`IL.defineOp({...})` を呼ぶ
2. **`index.html` と `_selfcheck.html` の両方**に `<script>` を1行ずつ足す
   （`_selfcheck.html` を忘れると、その処理を素通りしたまま「例外なし」と出ます）
3. `docs/_selftest.js` と `docs/_bench.js` の読み込みリストにも足す
4. カテゴリを増やすなら `js/registry.js` の `IL.categories` に追記

UI（処理リスト・パラメータ欄・解説パネル）は登録内容から自動で組み上がるので、
画面側を触る必要はありません。パラメータの型は
`range` / `select` / `checkbox` / `curve` / `spectrum`。
`when:` を書くと、他のパラメータの値に応じて表示・非表示を切り替えられます。

`curve`（トーンカーブ）と `spectrum`（スペクトルマスク）は絵で編集する型で、
`js/main.js` の `buildCurve` / `buildSpectrum` が中身です。この2つだけは
画面側にウィジェットの実装が要ります。

### 重い処理を Web Worker に逃がす手順

100 ms を超える処理を足すときは、`apply` の代わりに次を書きます。`apply` は自動で生えます。

| 書くもの | 中身 |
|---|---|
| `kernel(src, p, y0, y1, ctx)` | **行帯 `[y0, y1)` だけ**を処理して、高さ `y1-y0` の ImageData を返す |
| `prepare(src, p)` | 任意。重みの表など、帯をまたいで使い回す下ごしらえ |
| `cost(w, h, p)` | 任意。おおよそのミリ秒。Worker に回すかの判断だけに使う |
| `halo(p)` | 任意。帯の外を何行読むか。帯を薄くしすぎないための下限になる |
| `stages(p)` | 任意。段数（既定 1）。前の段の結果を次の段に入れる処理（反復など）向け |
| `route` | 任意。`'worker'` にすると軽くても必ずワーカーへ回る。**処理時間を見せる処理だけ**に立てる |
| `bench` | 任意。計測回数。1回空回ししてからこの回数まわし、最小を計算時間とする。`route` とセットで立てる |

`kernel` は**画像全体を読んで、書くのは帯だけ**にします。こうしておけば、
帯に切っても一枚で計算したのと1バイトも変わりません（`node docs/_selftest.js` が検査します）。

**帯に分けられない処理**（FFT のように画像全体を一度に扱うもの）は、`halo` に
画像の高さより大きい値を返してください。帯が1本にまとまり、丸ごと1つのワーカーへ渡ります。
並列にはなりませんが、計算中も画面は固まりません。この形の処理は
「`prepare` で最後まで作り、`kernel` はそこから行を切って返すだけ」と書きます
（`U.rowsOf(img, y0, y1)` がその切り出しです）。

`kernel` と `prepare` は Worker の中でも動くので、次の2つが制約です。

1. **外側の変数を参照しない。** 使ってよいのは `U.〇〇` と引数だけ
2. **`function (…) {…}` の形で書く。** メソッド短縮記法やアロー関数は文字列化できません

`U.〇〇` を新しく使いたくなったら、`js/core.js` の `U.workerExports` に名前を足してください。
`js/fft.js` のように別ファイルで `U` を増やす場合は、そのファイルの末尾で
`U.workerExports.push(...)` しても構いません（Blob を組み立てるのは最初の実行時なので、
それまでに足してあれば間に合います）。

### 画像のほかに数値を返す手順

PSNR のように、画像とは別に数値を画面へ出したいときは、`prepare` が返す `ctx` に
`report` を入れます。Worker 越しでもそのままページ側の
`onDone(dst, ms, how, used, report, cpu)` まで届き、
`js/main.js` が右下の stats 欄に並べます。

```js
prepare: function (src, p) {
  …
  return { out: img, report: { rows: [['PSNR', '31.2 dB']] } };
}
```

- `report.rows` … stats 欄に足す行 `[ラベル, 値]` の並び
- `report.tiles` … ビューアに重ねる見出し。横並び比較で使う（`viewer.setOverlay`）

`report` は Worker との間で構造化複製されるので、**数と文字列と配列だけ**で組みます。
関数や ImageData は入れられません。

### 処理の中から別の処理を呼ぶ手順

`U.opPrepare(id)` と `U.opKernel(id)` を使います（`IL.opById` を直接引くと
Worker の中で壊れます。あちらには `IL` が無いためです）。

```js
var c = U.opPrepare('median')(img, { radius: 1, iter: 1 });
var out = U.opKernel('median')(img, { radius: 1, iter: 1 }, 0, img.height, c);
```

「ノイズ除去の比較」がこの形で3手法を呼んでいます。アルゴリズムを写し取らずに済むので、
元の処理を直せば比較のほうも一緒に直ります。

### なぜ Worker のコードを文字列で組み立てているのか

`file://` のページからは、**外部ファイルの Worker が作れません**。

```
new Worker('js/kernel.js')
  → SecurityError: Script at 'file:///…' cannot be accessed from origin 'null'
```

Blob URL 経由なら通りますが、その Worker の中から `importScripts('js/core.js')` も
同じ理由で弾かれます（NetworkError）。そのため、

- `core.js` の `U`（`U.workerExports` に挙げたもの）
- 各 op の `kernel` と `prepare`

を `Function.prototype.toString()` で文字列に変換し、1つの Blob にまとめています。
処理の本体は `js/ops/*.js` に置いたまま動くので、アルゴリズムを二重に持つことにはなりません。
組み立てているのは `js/worker.js` の `buildSource()` で、`IL.jobs.source()` で中身を覗けます。

「ダブルクリックで開ける」を捨てればもっと素直に書けますが、
Zoom の画面共有中にサーバを立てる手順を挟みたくないので、この形にしています。

## 開発用のコマンド

```
node docs/_selftest.js          # 画像処理の中身を検証（641項目）
node docs/_bench.js 640 480     # 処理時間を計測
node docs/_gen_docs.js          # docs/処理解説.md を再生成
```

`_selftest.js` が見ているもの：

- 全処理が例外を出さず、サイズ・アルファ・NaN が正しいか
- 恒等になるべき設定で恒等になるか、各処理の性質（メディアンが孤立点を消す等）
- **自前の FFT が、定義どおりの DFT と一致するか**（n = 2 / 8 / 16 / 64）。
  往復して元に戻るか、正弦波が正しいビンに立つか、ノッチが周期ノイズを落とすか
- **マスクの格子番号が DC を中心に点対称か**（ここが半セルずれると共役対称が崩れ、
  逆変換の結果が濁る。ブラウザでは気づきにくいので数値で押さえている）
- **帯に切って計算しても、一枚で計算したのと1バイトも変わらないか**（step を4通り）
- **Worker 用に文字列化したコードが、別の実行文脈でそのまま動いて同じ結果を出すか**

後ろ2つが Worker 化の土台です。`kernel` の中でうっかり外側の変数を参照すると
ブラウザでしか出ない不具合になるので、ここで先に捕まえます。

`_selfcheck.html` はブラウザで開くと、全処理と全サンプルを順に叩いて
例外の有無・実行経路（Worker か否か）・canvas の寸法を左上に表示します。
UI を触ったあとの確認用です（index.html の DOM を写しているので、
index.html の構造を変えたらこちらも合わせてください）。

> **処理を1つ足したら、`index.html` と `_selfcheck.html` の両方に `<script>` を書くこと。**
> `_selfcheck.html` は自分の `<script>` に書いてある処理しか叩かないので、書き忘れると
> **その処理を素通りしたまま「例外なし」と出ます**（2026-09-06 に二値化と
> モルフォロジーで実際に起きました）。左上に出る「処理ボタン N 個」の数が
> `index.html` の処理数と合っているかで確かめられます。

**分離できるかどうかが、そのまま処理時間に出ます。**適応的二値化の「平均」は
積分画像なので、**窓の半径を 3 から 60 まで動かしても 13 ms のまま**。
モルフォロジーの四角と十字は「横→縦」の2段に分けられるので半径8でも 50 ms ですが、
**分けられない円は同じ半径で 305 ms** と6倍かかります。
どちらも実演で切り替えれば、工夫の値打ちがその場で読めます。

**画面で見比べるときは、右下の「計算時間」のほうを見てください。**
すぐ下の「画面に出るまで」は結果が返るまでの実時間で、経路によって意味が変わります
（軽くてメインスレッドで走る処理には直前の描画の割り込みが乗り、Worker に逃がした
処理では計算が別スレッドで進むぶん小さく出ます）。詳しくは次の節。

周波数領域の3処理・「ノイズ除去の比較」・二値化・モルフォロジー・デモザイクは、
分担はせず丸ごと1つのワーカーが受け持ちます。速くはなりませんが、計算中も画面は動きます。
理由はそれぞれ別で、FFT は画像全体を一度に扱うから、
比較のほうは PSNR / SSIM が画像全体の集計だから、
二値化は重い計算が prepare にあり帯に分けると各ワーカーがそれを繰り返すから、
モルフォロジーはオープニングの段で「収縮の結果が全部そろっている」必要があるから、
デモザイクは PSNR / SSIM に加えて AHD の方向選択が近傍を広く見るからです。
RGB は3チャンネルを別々に変換するので輝度のみの3倍かかります。

「ノイズ除去の比較」の 750 ms のうち、3手法の計算が約 470 ms、
PSNR / SSIM の4組が約 280 ms です。SSIM は 11×11 のガウシアン窓を
5回かける計算なので、数値のほうも安くはありません。

作業解像度 1600 以上では 2048×2048 の格子になり、RGB で3秒ほどかかります。
周波数領域は 640〜1024 での使用を想定しています。

行き先は `op.cost` の見積りが 120 ms を超えるかどうかで自動的に決まります。
軽いうちは同期実行のままです（往復させるとスライダーの追従が鈍るため）。
実際にどちらで動いたかは、画面右下の「実行」欄に出ます。

### 処理時間を見せる処理は、ベンチマークの作法で測る

二値化・モルフォロジー・アフィン変換・レンズ歪みの4つは、
どれも「設定を切り替えて処理時間を比べる」実演をします。
この4つだけ、次の2つを立ててあります。

| 指定 | 中身 |
|---|---|
| `route: 'worker'` | 見積りが軽くても必ずワーカーへ回す |
| `bench: 2` | 1回空回ししてから2回まわし、**最小**を計算時間として採る |

**1回きりの計測は当てになりません。**実測（Chrome・640×480）で、
**同じ設定・同じ経路のまま**モルフォロジーの円が 192 ms と 447 ms になりました（2.3倍）。
同じ回に、本来ほぼ同じはずの十字が四角の5〜6倍にもなっています。
じゃまが入る理由は3つ重なります。

1. メインスレッドで計算すると、ページの大きなデータ越しに走るのでごみ集め（GC）が挟まる
2. `Job.cancel()` はワーカーを `terminate()` するので、次の実行が**まっさらなワーカー**になり、
   コードがまだ最適化されていない状態で走る
3. PC 側が別の仕事（同期・ウイルス対策など）で混んでいる

**最小値**を採るのは、平均や中央値と違って
「じゃまが入らなければこの速さ」を指すからです。
`docs/_bench.js` が「1回空回ししてから3回計測してその中央値」を採っているのと同じ発想で、
**画面に出す数字をベンチマークとして使うなら、ベンチマークの作法で測る**というだけの話です。

代償として、この4つは計算が3回まわるので
**「画面に出るまで」が計算時間の3倍ほど**になります。
計算時間の欄には「（2回の最小）」と但し書きが出ます。

（この作法にたどり着くまでに、測り方を三度まちがえています。顛末は `_checklist.md` の項目29。）

### 右下に出る時間は2つあります

| 行 | 何を測っているか | 使いどころ |
|---|---|---|
| **計算時間** | `prepare` と `kernel` の中だけ（`Job` の `cpu`） | **処理どうしを比べるのはこちら** |
| **画面に出るまで** | ジョブを作ってから結果が返るまでの実時間（`ms`） | 体感の待ち時間 |

以前は後者だけを「処理時間」として出していましたが、これでは比較に使えません。
軽い処理は同期実行に回りますが、その順番待ち（`setTimeout` を1回はさむ）のあいだに
直前の描画やレイアウトが割り込むため、**50 ms の処理が 200 ms と出たり、
測るたびに数字が変わったり**します。逆に Worker 経路では計算が別スレッドで進むので、
実時間は「待った時間」であって「計算した時間」ではありません。
モルフォロジーの四角（同期）と円（Worker）を比べようとして、
四角のほうが遅く見える、ということが実際に起きました。

「計算時間」は計算している区間だけを測るので、経路が違っても素直に比べられます。
並列で走ったときは全ワーカーぶんの合計になり、「（8 並列の合計）」と但し書きが付きます。
**合計が実時間より大きいのは、分担が効いているという意味**です。

バイラテラルが重いのは実装の粗さではなく計算量そのものが O(N·k²) だからで、
Worker で分担しても**計算量は変わりません**。根本的に速くするには
bilateral grid のようなアルゴリズムの変更が要ります。

### 分担のしかた

画像を横に切って行帯に分け、ワーカー1つが連続した1区画を受け持ちます。
区画の中はさらに刻んで、焼き上がるたびに帯を送り返す作りです。
入力の複製はワーカーあたり1回で済み、進捗と逐次表示は細かく届きます。

スライダーを動かして次の計算が始まったら、走っている計算は捨てます。
順番待ちにすると、動かしたぶんだけ計算が積み上がってしまうためです。
重い設定のときは 90 ms だけ待ってから走らせ、ドラッグ途中の値は計算しません。

### 実演で分担のようすを見せる設定

既定の 640 では、いちばん重いバイラテラルでも8並列なら 0.1 秒で終わります。
**速すぎて進捗バーも逐次表示も目に映りません**（＝ふだんはこれが正しい状態）。

分担のようすを見せたいときは、作業解像度と σ を上げて計算量を戻してください。
12コア機での目安です。

| 設定 | かかる時間 | 見え方 |
|---|---:|---|
| 640・バイラテラル σ_space=3（既定） | 約 0.1 秒 | 一瞬。見えない |
| 640・バイラテラル σ_space=6 | 約 0.3 秒 | 帯が降りるのがぎりぎり見える |
| **1024・バイラテラル σ_space=6** | **約 0.7 秒** | **ちょうどよい。ここを推奨** |
| 1024・メディアン 半径5 | 約 0.7 秒 | 同上 |
| 1600・バイラテラル σ_space=6 | 約 1.7 秒 | じっくり見せられる |

「逐次表示を切って同じ設定で流す → 入れて流す」と並べると、
分担していることと、UI が生きていることの両方が同時に伝わります。
比較として、右下の「実行」欄に出る `Worker 8 並列` を指しておくと話がつながります。

### 周波数領域を実演するときの段取り

上から順に見せると話がつながります。URL の後ろのハッシュで、その状態を直接開けます。

| 順 | 開く状態 | 見せること |
|---|---|---|
| 1 | `#op=fft&sample=zone` | ゾーンプレートのスペクトルがリングになる。画像とスペクトルの対応 |
| 2 | `#op=fft&sample=geometry` | 直線に**直角**の向きに輝線が伸びる。エッジと周波数の関係 |
| 3 | `#op=fft&sample=periodic` | 中心から離れた場所に**孤立した輝点が1組**。これが縞の正体 |
| 4 | `#op=fftfilter&sample=periodic` | ノッチで輝点を潰す → 縞だけ消えて絵が戻る |
| 5 | `#op=fftmask&sample=periodic` | 同じことを**手で塗って**やる。ここが山場 |
| 6 | `#op=fftfilter&sample=fineline` | 切り方を「理想」にしてリンギング → 「ガウシアン」で消える |
| 7 | `#op=fft&sample=lowcontrast` | 「振幅だけ／位相だけで再構成」の見比べ |

3 → 4 → 5 が本筋です。「スペクトルのどこを触れば何が起きるか」を、
式（4）と手（5）の両方で見せると、周波数領域を扱う理由が伝わります。

6 の「境界処理」をゼロ詰めに切り替えると、スペクトルに十字が出ます。
これは画像に無い模様で、FFT が「画像は上下左右に繰り返している」と見なすために出るものです。
Hann 窓に切り替えると消えます。教科書の図でよく省かれる話なので、話の種になります。

### ノイズと評価を実演するときの段取り

| 順 | 開く状態 | 見せること |
|---|---|---|
| 1 | `#op=noise&sample=step` | 3種類のノイズを切り替える。ショットだけ**暗い段のほうが荒れる**（信号依存） |
| 2 | `#op=denoisecmp&sample=geometry` | 既定（ガウシアンノイズ）の4分割。**★が2つに割れる**（PSNR はバイラテラル／SSIM はガウシアン） |
| 3 | （2のまま）ノイズの種類を**ソルト＆ペッパー**へ | ★が両方とも**メディアンへ集まる**。PSNR は 14 dB 以上離れ、バイラテラルはほぼ効かない |
| 4 | （3のまま）表示を**メディアン（全解像度）**へ | 分割スライダーで原画と見比べ。粒が完全に消えている |
| 5 | （2に戻して）ガウシアンの σ を上げていく | **PSNR は σ=1.5 で頭打ち、SSIM は σ=3 まで伸びる** |
| 6 | `#op=noise` で「種類」を**周期ノイズ**へ。［PNG保存］して読み込み直し、`#op=fftmask` | **縞だけを抜いて絵は無傷**。ぼかしとの差が決定的に出る（下記） |

**3 が山場。**同じ画像・同じ道具立てで順位がひっくり返ります。
ソルト＆ペッパーでバイラテラルが効かないのが効きます（ノイズあり 18.5 dB に対して 19.1 dB）。
飛んだ画素は周りとかけ離れているので、バイラテラルがそれを「エッジ」と見なして
守ってしまうためです。得意技がそのまま裏目に出る例になります。

**2 と 5 は数値の読み方の話。**PSNR は誤差の大きさしか見ないのに対し、
SSIM は局所の平均・コントラスト・模様の並び方を見ます。バイラテラルは平坦なところに
残ったノイズを「エッジらしきもの」として守るので、誤差は小さいのにばらつきが残り、
SSIM で損をします。5 では「どこまでぼかすのが最適か」の答えが物差しによって倍も違う、
というところまで見せられます。

（上の数値は 320×240 の合成図形・ノイズ σ=20 での実測。サンプルや解像度で多少動きます）

### 周期ノイズ（斜め縞）── 2026-09-10 追加

**手持ちの写真に「わざと縞を乗せてから、スペクトルマスクで抜く」ための材料です。**
実写（印刷物の複写・パソコン画面・網戸ごしの風景）ではノイズの成分がスペクトルの帯に
散ってしまい、輝点を塗っても取れないことが分かったので足しました（2026-09-09 に実測。
最適な塗り方でも網の 6.5% しか落ちない）。合成の縞ならそうなりません。

- 乱数をまったく使いません。`g = f + A·sin(2π(u₀x + v₀y))` の1行で、
  **同じ座標には必ず同じ値が乗る**ので、行帯に切って分担しても継ぎ目は出ません
- **「縞の向き」に 0° と 90° を選ばないこと。**スペクトルの十字の上に乗り、
  輝点さがし（`IL.spectrumPeaks`）が十字を見ないので印が出ません
- **消すときは「筆の太さ 8・マスクの縁のぼかし 1」。**既定の「筆5・ぼかし2」だと
  落ち切りません（640×480 で 21.6 dB → 27.0 dB 止まり。筆8・ぼかし1 なら 43.6 dB）。
  **ぼかしは筆より小さく**が原則で、同じか大きいとマスクの谷が浅くなります
- **輝点は4つ出ます。**強い1組が本物、弱い1組は2の冪へ鏡映で広げたことの副産物
  （鏡の中では縞の傾きが左右反転する）。**本物だけ塗るほうが結果は良い**（43.6 対 41.1 dB）
- **白飛び・黒つぶれの多い絵には乗せないこと。**明るい背景（242）に振幅30を足すと 255 で
  頭打ちになり、サインの山が刈り取られて**基本波の2倍の位置にも輝点が立つ（倍音）**。
  印が6個になり、飽和で消えた情報は塗っても戻らない（`geometry` 33.9 dB 対
  `gaussnoise` 40.6 dB）。**チェックリストは `gaussnoise`、台本は写真C を指定してある**
- ぼかし（σ=2.5）で同じことをしようとすると 26.1 dB にしかならず、絵も潰れます。
  **周波数領域を使う理由が一往復で分かる**ので、実演の山場に据えられます

`_selfcheck.html` **22処理・例外なし**／`_checklist.md` の画面確認 **全48項目 合格**。

高速化の余地：

- いまはワーカーへ実行のたびに画像を送り直しています。ワーカー側に持たせたままにすれば、
  640×480 で 1回あたり十数 ms 削れます。ただし取り消しのたびにワーカーを作り直す作りと
  ぶつかるので、手はつけていません。
- スペクトルマスクを塗るたびに順変換からやり直しています。塗っている間は原画のスペクトルが
  変わらないので、順変換の結果を持ち回れば半分の時間で済みます（640×480・RGB で
  0.30 秒 → 0.19 秒ほど）。ワーカーに状態を持たせる作りが要るので、上と同じ理由で保留。
- 実数入力の FFT は、2行ぶんを1回の複素 FFT にまとめられます（実数 FFT の定石）。
  行方向の変換が半分になるので、全体で3割ほど速くなる見込みです。
- 「ノイズ除去の比較」は1つのワーカーが丸ごと受け持っています。ノイズも3手法も
  行帯に分けられる（ノイズが位置ハッシュなので分けても継ぎ目が出ない）ので、
  画像のほうだけなら複数コアで分担できます。妨げているのは PSNR / SSIM で、
  こちらは画像全体の集計なので帯ごとに出せません。帯ごとの部分和を集めて
  最後に足し合わせる作りにすれば分担できますが、`report` を1本の帯に乗せている
  いまの仕組みを、複数の帯から集める形に作り替える必要があります。
